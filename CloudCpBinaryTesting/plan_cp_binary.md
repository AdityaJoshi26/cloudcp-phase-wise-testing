# Cloudcp Binary Test Plan

Test plan for exercising the `cloudcp` binary using purpose-built datasets.

`cloudcp` reads a **batch file** (a NUL-framed list of source file paths), then
uploads every listed file to an object store. Invocation under test:

```bash
/opt/bryck/aws/bin/cloudcp \
  "/opt/bryck/bryckapi/downloads/bcloud_batchmeta/transfer_103/batches/inprogress/small/batch_001611.txt" \
  --bucket "aditya" \
  --fs-prefix "/bryck/1mb_halfmill" \
  --transfer-id 103 \
  --prefix "cloudcp_test2" \
  --endpoint-url https://10.10.10.103:9000
```

Key mechanics that the datasets must stress:
- **`--fs-prefix`** is stripped from each local path; **`--prefix`** is prepended to
  form the object key. So the local files must live under the `--fs-prefix` root.
- Batch files are **NUL-terminated raw path bytes** (paths may contain spaces,
  newlines, non-UTF-8 bytes). The parser must handle all of these.
- Files are grouped into **size tiers** (see below), which drive batch size,
  target batch bytes, and multipart/chunk behaviour.

---

## 1. Pipeline Overview

```
datagen --spec <spec>.yaml     ->  materialize real files on disk (the DATASET)
                                    (under the --fs-prefix root, e.g. /bryck/1mb_halfmill)
make_batches.py <dataset_dir>  ->  NUL-framed batch_XXXXXX.txt files (POSITIVE)
make_batches.py --negative     ->  malformed / hostile files + batch files (NEGATIVE)
cloudcp <batch_file> ...       ->  the program under test
```

The `datagen` tool cannot produce negative/corrupt artifacts (broken symlinks,
unreadable files, malformed batch framing, dangling paths, etc.). Those are
generated by the new `--negative` / `-n` mode added to `make_batches.py`.

---

## 2. Size Tiers (from `BatchBuilder.classify_bucket`)

A file is classified into the first tier whose limit it is *below*:

| Tier     | Size range              | Why it matters for cloudcp                                  |
|----------|-------------------------|-------------------------------------------------------------|
| `zero`   | exactly 0 bytes         | Empty-object handling; zero-length PUT.                     |
| `tiny`   | 1 B – < 1 MiB           | High file count / throughput; single-part PUT.             |
| `small`  | 1 MiB – < 64 MiB        | Crosses the 8 MiB `upload_cutoff` -> multipart begins.     |
| `medium` | 64 MiB – < 1024 MiB     | Many multipart chunks (8 MiB chunk_size).                  |
| `large`  | >= 1024 MiB (1 GiB+)    | Large multipart; long-running transfer; resume/retry.      |

The datasets below deliberately place files on **both sides of tier boundaries**
(0, ~1 MiB, ~64 MiB, ~1 GiB) and across the **8 MiB multipart cutoff**.

## 3. Positive Datasets (datagen spec files)

All specs live in `CloudcpBinaryTesting/specs/`. Each `root:` should be set to a
path under the `--fs-prefix` root before running (defaults below use
`/bryck/1mb_halfmill/cloudcp_test`).

| # | Spec file                     | Mode      | What it tests                                                                 |
|---|-------------------------------|-----------|-------------------------------------------------------------------------------|
| 1 | `01_zero_byte.yaml`           | flat      | `zero` tier — 200 empty (0-byte) files.                                        |
| 2 | `02_tiny_files.yaml`          | tree      | `tiny` tier — thousands of small files (1 KiB–256 KiB), throughput.           |
| 3 | `03_small_files.yaml`         | flat      | `small` tier — 1–16 MiB, straddles the 8 MiB multipart cutoff.                |
| 4 | `04_medium_files.yaml`        | flat      | `medium` tier — 64–512 MiB, multi-chunk multipart.                            |
| 5 | `05_large_files.yaml`         | flat      | `large` tier — 1–5 GiB, sparse content to save disk, big multipart.           |
| 6 | `06_sparse_files.yaml`        | flat      | Sparse (`ftruncate`) files across tiers — logical vs physical size.           |
| 7 | `07_fill_files.yaml`          | flat      | Deterministic `fill` content (0x00) — stable checksum verification.           |
| 8 | `08_deep_tree.yaml`           | tree      | Deep nested directory paths (fanout 4 x depth 5) — long keys.                 |
| 9 | `09_unicode_names.yaml`       | flat      | Unicode/emoji/CJK/Cyrillic + spaces in names — path encoding round-trip.      |
|10 | `10_special_char_names.yaml`  | flat      | ASCII special chars (spaces, parens, `&`, brackets) — shell/key edge cases.   |
|11 | `11_mixed_realistic.yaml`     | tree      | Weighted mix of extensions/sizes (log-uniform) — realistic workload.          |
|12 | `12_tiny_2million.yaml`       | tree      | **Scale** — ~2,000,000 tiny files (512 B–16 KiB), enumeration/batch stress.    |

Notes:
- Specs 1–4, 7–11 use `content.type: random` so uploaded checksums are meaningful.
- Specs 5–6 use `sparse` to avoid consuming terabytes of local disk while still
  producing large *logical* sizes for the transfer path.
- Unicode/special-char specs (9, 10) mirror the sample batch we inspected
  (accented, Cyrillic, CJK names, embedded spaces) and validate the NUL framing
  end-to-end.

## 4. Negative Datasets (`make_batches.py --negative`)

`datagen` cannot create these, so `make_batches.py --negative` builds a
`negative_data/` directory of hostile filesystem objects **and** a set of
malformed batch files. Each is a distinct, independently runnable test case.

### 4a. Hostile filesystem objects (real files under `negative_data/`)

| ID   | Object                          | Expected cloudcp behaviour (to verify)                    |
|------|---------------------------------|-----------------------------------------------------------|
| N01  | Broken symlink (dangling target)| Skip + error, do not crash.                               |
| N02  | Symlink -> real file            | Defined policy (follow or skip); no infinite loop.        |
| N03  | Symlink -> directory            | Not treated as a file; skipped/handled.                   |
| N04  | Unreadable file (`chmod 000`)   | Permission-denied surfaced as per-file error, run continues.|
| N05  | Named pipe / FIFO               | Not treated as a regular file; skipped.                   |
| N06  | Zero-byte file                  | Valid edge — uploaded as empty object.                    |
| N07  | Name with embedded spaces       | Key preserved verbatim.                                   |
| N08  | Name with embedded newline / CR | Framing preserved (NUL delimiter), key correct.           |
| N09  | Non-UTF-8 / surrogate-escape name| Byte-exact round-trip, no decode crash.                  |
| N10  | Very long name (~255 bytes)     | Handled up to `NAME_MAX`; graceful error beyond.          |
| N11  | Very deep / long path (~PATH_MAX)| Handled up to `PATH_MAX`; graceful error beyond.         |

(POSIX-only objects — symlinks, FIFO, `chmod 000`, newline/non-UTF-8 names — are
created on Linux/macOS; on Windows they are skipped with a logged notice, since
`cloudcp` itself runs on Linux.)

### 4b. Malformed / hostile batch files (framing tests)

| ID   | Batch file                       | Malformation                                              |
|------|----------------------------------|-----------------------------------------------------------|
| B01  | `bad_batch_empty.txt`            | 0 bytes (no records).                                     |
| B02  | `bad_batch_no_terminator.txt`    | Last path missing its trailing NUL.                       |
| B03  | `bad_batch_double_nul.txt`       | Two consecutive NULs (empty record in the middle).        |
| B04  | `bad_batch_leading_nul.txt`      | Starts with a NUL (empty first record).                   |
| B05  | `bad_batch_only_nuls.txt`        | Nothing but NUL bytes.                                     |
| B06  | `bad_batch_dangling_paths.txt`   | Well-framed, but paths do not exist on disk.              |
| B07  | `bad_batch_directory_entry.txt`  | A directory path where a file is expected.                |
| B08  | `bad_batch_crlf_paths.txt`       | Paths containing embedded CR/LF (valid via NUL framing).  |
| B09  | `bad_batch_nonutf8.txt`          | Path with non-UTF-8 / surrogate bytes.                    |
| B10  | `bad_batch_very_long_path.txt`   | Single path far exceeding `PATH_MAX`.                     |
| B11  | `bad_batch_whitespace_only.txt`  | A record that is only spaces/tabs, then NUL.              |
| B12  | `bad_batch_mixed_valid_invalid.txt`| Alternating valid and dangling paths (partial success).|

Expected overall: `cloudcp` reports per-record errors, keeps a clean exit-code
contract, never crashes/segfaults, and (for B12) transfers the valid records
while reporting the invalid ones.

## 6. Execution Steps (after approval)

```bash
# 1. Materialize positive datasets (run each spec; set root under --fs-prefix)
for s in CloudcpBinaryTesting/specs/*.yaml; do ./build/datagen --spec "$s"; done

# 2. Build positive batch files from the materialized data
python make_batches.py /bryck/1mb_halfmill/cloudcp_test \
    -o CloudcpBinaryTesting/batches --batch-size 500

# 3. Build the negative suite (hostile files + malformed batches)
python make_batches.py --negative -o CloudcpBinaryTesting

# 4. Run cloudcp against each batch file and record results
/opt/bryck/aws/bin/cloudcp "CloudcpBinaryTesting/batches/small/batch_000000.txt" \
    --bucket aditya --fs-prefix /bryck/1mb_halfmill \
    --transfer-id 103 --prefix cloudcp_test --endpoint-url https://10.10.10.103:9000
```

## 7. Pass / Fail Criteria

- **Positive:** every listed file uploads; object size (and checksum where
  content is deterministic) matches source; keys equal
  `<prefix>/<path-with-fs-prefix-stripped>`; correct exit code.
- **Negative:** no crash/hang/segfault; each bad object/record produces a clear,
  attributable error; valid records in a mixed batch still succeed; exit code
  reflects partial vs total failure per the binary's contract.
- **Encoding:** unicode/space/newline/non-UTF-8 names round-trip byte-exact.
- **Tiers:** files land in the expected tier and use the expected
  single-part vs multipart path around the 8 MiB cutoff.
